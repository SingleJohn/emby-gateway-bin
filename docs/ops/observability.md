# 播放与流量监控

管理界面「监控」分组下有四个页面：实时播放、流量分析、用户与媒体、访问来源。本页逐个说明它们能看到什么、适合回答什么问题，以及统计口径和数据保留时间。

## 先理解数据从哪里来

网关只能统计**经过它的请求**：

- 播放请求被 302 跳转后，播放器会直接从存储（S3、CDN、网盘等）下载视频。这部分下载流量不经过网关，所以看不到。网关记录的是「发出了一次 302，指向哪个后端，用了多长时间」。
- 由网关代理或中转（Relay）的请求，响应内容会流经网关，这部分流量会计入「下行流量」和「观测流量」。
- 用户名、媒体名称等信息在请求发生后异步补全，刚发生的请求可能暂时缺少这些字段。

所以「今日下行流量」通常远小于用户实际观看的数据量，这是正常的，说明大部分流量已经由存储直接提供。

## 实时播放

位置：<span class="ui-path">监控 › 实时播放</span>

<Shot name="obs-live" alt="实时播放：正在播放的会话卡片与并发趋势" />

显示此刻正在进行的播放，每 5 秒刷新一次，可以按 Emby 源筛选，在卡片和表格两种视图之间切换。

::: warning 需要先打开会话统计
实时播放的数据来自网关自己的播放会话计数。需要在 <span class="ui-path">安全 › 防护策略</span> 的「播放限制」中打开「统计播放会话」（只记录、不拦截）或「强制并发限制」，这里才会有数据。详见 [防护策略](/guide/security)。
:::

- **顶部指标**：正在播放（当前并发播放流）、在看用户（去重后的在播用户数）、并发限制（每人默认可同时播放几路）、额度已满（再开一路就会被拒绝的用户数）。
- **会话卡片**：每路播放显示媒体名称、用户、客户端和设备、来源 IP、所属 Emby 源、已播放时长，以及该用户的并发额度占用情况（例如 `1 / 2`，不限制时显示 `∞`）。
- **更多操作**：每张卡片的菜单里可以「查看该用户播放记录」「查看该 IP 的拦截记录」，或者「释放该用户会话计数」。

::: tip 释放会话计数不会中断播放
「释放该用户会话计数」只清零网关里该用户在这个 Emby 源上的会话计数。客户端正在播放的内容不受影响，但该用户可以立即再开新的播放。适合用来处理客户端异常退出、计数没有及时释放的情况。
:::

- **并发趋势**：活跃路数和活跃用户的折线图，由浏览器每 5 秒采样一次，只保留当前页面最近 5 分钟，刷新页面后会重新开始。
- **按 Emby 源分布**：并发集中在哪个源。

## 流量分析

位置：<span class="ui-path">监控 › 流量分析</span>

<Shot name="obs-traffic" alt="流量分析：概览指标与趋势图" />

请求级别的流量视图。顶部工具栏可以选择 Emby 源、请求范围（全部请求、普通 API、媒体请求）、请求来源（Proxy 流量或 Admin 操作），以及统计天数（近 7 天、30 天或 90 天）；打开「实时追踪」后数据会持续刷新。页面分三个 Tab。

### 概览

- **指标卡**：所选范围的请求数、302 重定向次数、下行流量、平均延迟、4xx 客户端错误、5xx 服务端错误。
- **请求量与下行流量**：双轴趋势图，左轴请求数，右轴 GiB。
- **每日状态构成**：每天各状态码的请求量。
- **延迟趋势**：均值画成折线，峰值单独一列，避免被均值压平。
- **直链命中率**：302 占总请求的比例，是衡量网关是否在正常分流的核心指标。
- 每日明细表：日期、请求数、302、4xx、5xx、下行流量。

### 请求日志

逐条查看经过网关的请求，可以按状态码、客户端 IP、路径前缀和关键词筛选。点击一条记录可以打开详情，里面有：

- 基本信息：状态码、方法、路径与参数、请求范围、耗时、下行字节数。
- 播放相关：媒体 Item、PlaySession、客户端与设备、Emby 用户。
- 302 相关：命中的后端（Redirect Backend）、对象路径（Object Key）、跳转地址（Location），以及各阶段耗时（Redirect Trace）。
- 来源：IP 及归属地、Emby 源、上游、User-Agent、Referer、请求头。

排查「为什么这次播放没有走 302」时，先在这里找到那条请求，看它的状态码和 Redirect 字段。

### 302 链路

专门分析直链跳转：

- **302 后端分布**：统计窗口内每个后端发出了多少次直链。
- **链路阶段耗时**：网关生成一次 302 的各个阶段（如向 Emby 查询媒体路径、路由判断、路径映射、生成直链）的 P50、P95 和最大值，用来定位慢在哪一步。
- **按后端成功率**：每个后端的尝试次数、成功率和 P95 耗时。某个后端成功率低，往往是它的凭据、配额或网络出了问题。
- **Top 用户 / Top 客户端 IP**：谁触发的直链最多，IP 带归属地。

可以按后端、用户名、客户端 IP 和路径前缀筛选。

## 用户与媒体

位置：<span class="ui-path">监控 › 用户与媒体</span>

<Shot name="obs-media" alt="用户与媒体：交付方式构成与播放趋势" />

回答「谁在看、看了多少、是怎么交付的」。时间范围可选近 24 小时、7 天、30 天、90 天。分三个 Tab：

### 媒体请求

- **指标卡**：媒体请求数、302 重定向、网关代理、观测流量、播放尝试数、活跃用户。
- **交付方式构成**：302 重定向、网关代理、状态上报、播放信息各占多少。只有实际流经网关的响应内容才计入「观测流量」。
- **播放尝试数趋势**：按播放会话去重，比单纯的请求数更接近真实观看次数。
- **请求类型分布**：视频、音频、HLS、字幕、下载等。
- **Top 10 用户播放时长**：取自当前使用统计的查询结果。
- **请求明细**：可以按请求类型（视频、音频、HLS、播放信息、播放上报、字幕、下载、直链入口）、交付方式、防护分组、请求特征（疑似预取或探测、重复准备）和状态码筛选。

### 使用统计

按用户汇总：播放次数、会话时长、请求数、直链次数、代理流量，以及用过的设备、客户端、IP 数量，最近看过的媒体、常用客户端和设备、最近 IP。各列都可以排序，适合排查账号共享。

### 播放记录

最近的播放历史，包括开始和结束时间、Emby 源、用户、媒体、客户端与设备、IP、时长、结束原因，以及记录质量：「完整」表示整场播放都被观测到；「部分观测」表示只观测到其中一部分。

## 访问来源

位置：<span class="ui-path">监控 › 访问来源</span>

<Shot name="obs-access" alt="访问来源：Top 客户端 IP 与地区分布" />

客户端 IP 的地理和网络分布，用来识别异常来源和账号分享。可以按 Emby 源筛选，并在「全部请求」和「仅 302 直链」之间切换。

- **指标卡**：总请求数、出现过的国家或地区数、Top IP 数（排行榜长度，不是独立 IP 总数）、待解析 IP（还没查到归属地的 IP 数）。
- **Top 客户端 IP**：按请求数排序，显示占比、归属地、运营商和 IP 类型。每一行有两个按钮：
  - 「请求日志」：跳到流量分析的请求日志，并自动按这个 IP 筛选。
  - 「拦截记录」：跳到防护记录，查看这个 IP 被拦截的情况。
- **地区与网络**：Top 省份或地区、国家或地区分布、IP 类型构成（家宽或 IDC）、Top 运营商、大区分布。

::: tip IDC 占比偏高要留意
正常家庭用户大多是家宽 IP。如果 IDC（机房）IP 占比明显偏高，通常意味着有人通过代理访问，或者在批量抓取。
:::

IP 归属地由网关调用第三方查询接口获得，结果会缓存。接口选择和缓存天数在 <span class="ui-path">系统 › 系统设置</span> 的「IP 归属地查询配置」中设置，见 [系统设置](/guide/system-settings#ip-归属地查询)。

## 小技巧：带着 IP 跳转

流量分析支持在网址里带上 IP 直接筛选，例如 `#/observability/traffic?tab=logs&ip=203.0.113.8`。访问来源页的「请求日志」按钮用的就是这种方式。管理界面的筛选条件都会写进网址，可以直接把链接发给同事。

## 数据保留

保留时间在 <span class="ui-path">系统 › 系统设置</span> 的「全局设置」中修改：

| 数据 | 设置项 | 默认值 |
|---|---|---|
| 请求日志（流量分析的请求明细） | 请求日志保留天数（`request_log_retention_days`） | 30 天 |
| 每日统计、播放记录、媒体访问统计 | 统计保留天数（`stat_retention_days`） | 180 天 |
| 安全事件与告警记录 | 固定，不可修改 | 90 天 |

网关启动时和之后每 30 分钟会清理一次过期数据，保存系统设置后也会立即触发一次。PostgreSQL 与 SQLite 在磁盘空间回收上的差别，见 [数据库维护](/ops/database-maintenance)。

同一处还有两个写库参数：「DB 批量写入条数」（`db_batch_size`，默认 200，最大 1000）和「DB 刷新间隔(ms)」（`db_flush_interval_ms`，默认 1000，最小 200）。请求日志先在内存中攒批，再批量写入数据库。一般不需要调整；只有在请求量很大、数据库写入跟不上时，才考虑调大批量。

## 统计口径的常见疑问

- **控制台和流量分析的数字对不上**：先确认两边选的是同一个 Emby 源、同一个时间范围和同一种请求范围。
- **按天统计的边界**：每日统计按网关所在系统的时区划分日期，容器部署时请设置 `TZ`。
- **刚播放的记录没有用户名**：用户和媒体信息是异步补全的，稍等片刻再刷新。

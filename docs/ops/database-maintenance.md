# 数据库维护

数据库维护页用于查看请求日志占用并清理 PostgreSQL 分区。只有全局管理员可访问和执行操作。

## 页面位置

进入「系统 → 网关配置」，滚动到「数据库维护」。页面展示：

- 数据库总占用
- 访问日志数据、索引和合计大小
- 请求日志预估行数
- `daily_stats` 大小
- 各请求日志分区的数据、索引和预估行数
- 当前保留天数与过期清理预览

## PostgreSQL 分区

`request_logs` 按 `created_at` 月分区。完整删除过期分区会释放该分区的数据和索引文件，适合解决实际磁盘占用。

保留天数可能落在当前月份中间。为了避免删除仍需保留的记录，系统只删除完整过期分区，因此当前月内已经超过天数阈值的部分记录可能暂时保留。

## 清理模式

### 清理过期分区

根据 `request_log_retention_days` 计算截止时间，只处理完整过期分区。

### 清空访问日志

删除所有 `request_logs` 分区数据。该操作不可恢复，但仍保留聚合统计。

两种模式都明确保留 `daily_stats`。

## 安全执行流程

1. 确认 PostgreSQL 备份可用。
2. 查看维护状态和每个分区大小。
3. 点击清理动作，先查看预览中的分区、行数和预计空间。
4. 核对确认文本和模式。
5. 执行后比较清理前后字节数和释放空间。
6. 回到观测中心确认聚合趋势仍可用。

清理期间不要同时调整自动保留策略或重复提交相同操作。

## SQLite 说明

手动分区清理只支持 PostgreSQL。SQLite 没有月分区，即使执行 `DELETE`，数据库文件也不一定立即缩小；它需要单独评估 checkpoint/VACUUM，当前管理页不会替你执行这些操作。

## 自动保留

后台会周期检查请求日志保留期。自动任务和手动清理都应以相同的保留天数为准。

如果磁盘仍持续增长：

1. 检查当前月分区增长速度。
2. 检查请求日志是否记录了过大的 Header 或 trace。
3. 确认自动保留任务没有持续报错。
4. 根据业务审计要求调整保留天数，而不是直接关闭日志。

## 不应执行的操作

- 不要在没有备份时手工 `DROP` 配置或统计表。
- 不要把普通 `DELETE` 的逻辑空闲空间当作磁盘已释放。
- 不要为了缩小数据库文件清除 `daily_stats`，除非业务明确不再需要历史聚合。
- 不要在不了解迁移影响时开启 `GATEWAY_DB_ALLOW_DESTRUCTIVE_MIGRATIONS`。
